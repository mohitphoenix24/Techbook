An agent that queries data is only as good as its understanding of that data. Before any model is involved, we need a database worth asking questions of, and we need to be clear about what its words *mean*.

## Why a generated shop

DataPilot ships with a small online shop called **Aurora**: customers, products, orders and the lines of each order. It is **generated by code from a seed**, not stored as a file in the repository, for three reasons:

- **Everyone gets the same data.** The same seed always yields the same shop, so the tests, the evals and the numbers in this lesson are the same on your machine as on mine.
- **It is not real data**, so there is nothing private to protect while learning.
- **You can change it.** A different seed or size gives you a new shop, and a test can build a tiny one.

Three details of the design matter for the agent:

1. **`order_items.unit_price` is the price at the time of the order**, copied from the catalogue. Prices change; history must not.
2. **Dates are text in `YYYY-MM-DD` form.** SQLite has no date type, but this format sorts correctly and `substr(ordered_on, 1, 7)` gives the month.
3. **`DESCRIPTIONS` is not decoration.** It travels to the model (through the tools) and states the *business rules*.

## "Revenue" is a decision

Ask five people for last month's revenue and you may get five answers. Is a cancelled order revenue? A returned one? An order that is shipped but not yet delivered? The data cannot say; a *definition* must.

In Aurora: **revenue counts only orders whose status is `delivered` or `shipped`.** Cancelled and returned orders earned nothing. A line's value is `quantity * unit_price`.

This single rule is the difference between a correct answer and a plausible wrong one. If the model forgets it, revenue is overstated and nobody gets an error. That is why the rule appears in three places: in the table descriptions the tools return, in the system prompt (lesson 5), and in the golden queries the eval uses (lesson 9). **Business definitions belong in the data layer the agent can read, not in people's heads.**

Look at the realism, because realism is what makes questions interesting:

- **Skew:** every ninth customer is weighted three times as likely to order, so a few customers matter far more (the "top customers" question has a real answer).
- **Seasonality:** `MONTH_WEIGHT` makes the two ends of the year (festive months) busier.
- **Status mix:** about 78% delivered, 6% shipped, 9% cancelled, 7% returned.
- **Currency and places:** rupees, mostly Indian cities, with a few in Dubai, Singapore, London and New York, so "by country" has something to say.
- **The data ends mid-October 2026** (`date(2026, 10, 12)`), and the system prompt tells the model today's date, so "last month" has a meaning.

## Build it and ask it questions

This block runs the real `seed.py` in your browser (Python's built-in `sqlite3` is part of the runtime) and then queries the shop. It also shows why the revenue rule matters: the same sum, with and without it.

```python run src="data-pilot/backend/app/seed.py#imports+schema+data+build" title="Build the shop and query it" level=intermediate
conn = sqlite3.connect(":memory:")
build_database(conn)                       # same seed, same shop, on every computer

for table in ("customers", "products", "orders", "order_items"):
    print(f"{table:<12}", conn.execute(f"SELECT COUNT(*) FROM {table}").fetchone()[0], "rows")

print("\norders by status:")
for status, n in conn.execute("SELECT status, COUNT(*) FROM orders GROUP BY status ORDER BY 2 DESC"):
    print(f"  {status:<10}{n:>4}")

line = "SELECT SUM(i.quantity * i.unit_price) FROM order_items i JOIN orders o ON o.id = i.order_id"
everything = conn.execute(line).fetchone()[0]
paid = conn.execute(line + " WHERE o.status IN ('delivered', 'shipped')").fetchone()[0]
print(f"\nrevenue counting every order: ₹{everything:,.0f}")
print(f"revenue by the business rule: ₹{paid:,.0f}   ({100 * (everything - paid) / everything:.1f}% of 'sales' never earned anything)")

print("\ntop 3 customers by revenue:")
top = conn.execute(f"""SELECT c.name, c.city, ROUND(SUM(i.quantity * i.unit_price)) AS revenue
                       FROM customers c JOIN orders o ON o.customer_id = c.id JOIN order_items i ON i.order_id = o.id
                       WHERE o.status IN ('delivered', 'shipped') GROUP BY c.id ORDER BY revenue DESC LIMIT 3""")
for name, city, revenue in top:
    print(f"  {name:<18}{city:<10}₹{revenue:,.0f}")
```

Change the query: group by `channel`, by `substr(o.ordered_on, 1, 7)`, or add a `LIMIT`. Everything an agent will do later is just *this*, chosen by a model.

:::note Two sentences of SQL you will meet constantly
`GROUP BY` collapses rows into groups and lets you compute one number per group (`SUM`, `COUNT`, `AVG`). A `JOIN ... ON` lines up rows from two tables (here: each order item with its order, so you can use the order's status). Almost every business question is "join, filter, group, sort".
:::

## The tests

```python src="data-pilot/backend/tests/test_seed_and_guard.py" region="seed-tests" title="backend/tests/test_seed_and_guard.py"
```

The tests pin down the *shape* (four tables, 60 customers, 24 products, 420 orders, four statuses, the date range), **determinism** (same seed, same shop; a different seed, a different one) and **integrity** (no orders pointing at missing customers, and every unit price equal to the catalogue price). A change to the seed that breaks one of these breaks every eval built on top of it, so you want to know immediately.

:::keypoints
- A generated, seeded database gives every learner and every test the same data, with nothing private in it.
- Words like "revenue" are decisions. Write the definition where the agent can read it (table descriptions, the system prompt) and test it.
- Realistic skew, seasonality and mix are what make questions about the data interesting.
- Store prices (and other facts that change) on the line item, so history stays true.
- Test the shape, determinism and integrity of data your evals depend on.
:::
