A **vision-language model (VLM)** takes an image (or video) plus a text instruction and writes text: *"What is on the pallet?"*, *"Read the label"*, *"Is the gripper holding the bolt?"* It joins the vision features of the previous lessons with a **large language model (LLM)**.

## The standard recipe

:::flow Typical VLM
Vision encoder | A pre-trained ViT, usually CLIP/SigLIP, turns the image into a grid of patch features (for example 24 × 24 = 576 vectors).
Connector (projector) | Maps the visual features into the LLM's word-embedding space: a linear layer or 2-layer MLP (LLaVA), a perceiver/Q-Former that squeezes to a fixed number of queries (Flamingo, BLIP-2), or pixel-shuffle token merging.
Language model | A decoder-only LLM (Vicuna, Llama, Gemma, Qwen, Mistral...). Image tokens are inserted in the sequence like words, followed by the text prompt.
Output | The LLM generates the answer token by token, trained with the ordinary next-token loss on the text.
:::

So an image becomes, say, 576 "visual words" in front of the question. The LLM attends to them like any other tokens.

## Counting the tokens (and the cost)

```python run title="How many image tokens, and what does that cost?" level=intermediate
import numpy as np

def tokens(res, patch, merge=1, tiles=1):
    side = res // patch // merge
    return side * side * tiles

print("Encoder setting                              | visual tokens | LLM context used")
for name, res, patch, merge, tiles in [
    ("CLIP ViT-L/14 @ 336, no merge (LLaVA-1.5)", 336, 14, 1, 1),
    ("SigLIP-so400m/14 @ 384, 2x2 merge",         384, 14, 2, 1),
    ("same, 4 tiles + 1 thumbnail (any-res)",       384, 14, 2, 5),
    ("ViT-B/16 @ 224",                              224, 16, 1, 1),
    ("high-res document page, 8x8 tiles",           448, 14, 2, 64),
]:
    n = tokens(res, patch, merge, tiles)
    print(f"{name:<45}| {n:>8}      | {n} tokens ({n / 4096:.0%} of a 4k window)")

# self-attention cost in the LLM grows with the square of the sequence length
for n in (576, 2304, 9000):
    print(f"sequence of {n:>5} tokens: attention matrix entries per layer per head = {n * n:,}")
print("so: high resolution = more tokens = slower and costlier; token merging/pooling is a main trick for efficiency")
```

## Training in stages (LLaVA style)

1. **Alignment (pre-training)**: freeze the vision encoder and the LLM; train **only the connector** on image–caption pairs (a few hundred thousand to millions) so that visual features "speak" the LLM's language.
2. **Instruction tuning**: train the connector **and the LLM** (often with LoRA) on image–instruction–answer conversations (VQA, reasoning, OCR, dialogue), many generated by a stronger model like GPT-4 from captions and boxes.
3. (Sometimes) **Unfreeze the vision encoder** late, add high-resolution data, then preference tuning (RLHF/DPO) to reduce hallucinations.

```python local check title="A LLaVA-style connector: project visual features and prepend them to text embeddings"
import torch
from torch import nn

torch.manual_seed(0)
B, n_vis, d_vis, d_llm, n_txt, vocab = 2, 16, 64, 128, 6, 1000

vision_features = torch.randn(B, n_vis, d_vis)                    # output of a frozen ViT: one vector per patch
connector = nn.Sequential(nn.Linear(d_vis, d_llm), nn.GELU(), nn.Linear(d_llm, d_llm))   # the trainable projector (2-layer MLP)
embed = nn.Embedding(vocab, d_llm)                                # the LLM's own word embeddings (frozen)
text_ids = torch.randint(0, vocab, (B, n_txt))

visual_tokens = connector(vision_features)                        # (B, 16, d_llm): "visual words"
sequence = torch.cat([visual_tokens, embed(text_ids)], dim=1)     # image tokens first, then the question
print("LLM input sequence:", tuple(sequence.shape), "= 16 image tokens + 6 text tokens")

# causal mask: text tokens may look at all image tokens, image tokens may not look ahead at text
n = sequence.shape[1]
causal = torch.tril(torch.ones(n, n, dtype=torch.bool))
print("last text token can see", int(causal[-1].sum()), "of", n, "tokens; the first image token sees", int(causal[0].sum()))
trainable = sum(p.numel() for p in connector.parameters())
print("trainable parameters in stage 1 (only the connector):", trainable)
frozen_proxy = sum(p.numel() for p in embed.parameters())
print("frozen parameters in this toy (embedding table only):", frozen_proxy, "- in a real model the frozen LLM has billions")
```

## Model families

| Model | Key idea |
|---|---|
| **Flamingo** (DeepMind) | Frozen LLM; a **Perceiver Resampler** compresses visual features; new **gated cross-attention** layers inserted into the LLM; strong few-shot in-context learning |
| **BLIP / BLIP-2** | **Q-Former**: a small transformer with learned queries bridging a frozen image encoder and a frozen LLM; cheap to train |
| **LLaVA / LLaVA-1.5 / NeXT** | CLIP encoder + MLP + Vicuna/Llama; the simple, strong open recipe; any-resolution tiling |
| **MiniGPT-4, InstructBLIP** | Variants with Q-Former and instruction tuning |
| **PaliGemma / PaLI** | SigLIP encoder + Gemma; trained to caption, answer, detect and segment with special location tokens |
| **Qwen-VL / Qwen2-VL / InternVL** | Native dynamic resolution, strong OCR/documents, video, grounding |
| **Idefics, Molmo, Phi-Vision, SmolVLM** | Open and small models; Molmo adds pointing |
| **GPT-4o/4V, Gemini, Claude** | Closed multimodal models; natively multimodal |

## What VLMs do well

- **Visual question answering (VQA)** and **captioning**; **document and chart understanding**; **OCR-free reading** of receipts, forms and screens.
- **Grounding**: output boxes or points as text ("<loc0123>..." in PaliGemma, `[x1,y1,x2,y2]` in Qwen-VL), i.e. detection by language; **referring expressions** ("the red box on the left").
- **Reasoning over images** and following complicated instructions; **video QA** with frame sampling.
- **Robotics**: scene descriptions, task planning, success detection, and **VLA models** (vision-language-action: RT-2, OpenVLA, π0) which output robot actions as tokens (see the robotics module).

## Where they fail

- **Hallucination**: describing objects that are not there; **counting** and **spatial relations** ("which is left"); small text; **fine-grained** differences.
- **Resolution limits**: tiny objects vanish after patching and merging.
- **Latency and cost**: a billion-parameter LLM for every frame; use for rare, high-value decisions or on cached/keyframes, not for every pixel at 30 FPS.
- **No guarantee of format**: ask for JSON and validate it; use constrained decoding.

## Evaluating VLMs

Benchmarks: **VQAv2, GQA, TextVQA, DocVQA, ChartQA, MMMU, MMBench, POPE (hallucination), MME, RealWorldQA**. For your own use, build a **task-specific test set** (50–200 real images with the exact question and expected answer), measure accuracy and failure types, and try different prompts. Do **not** trust public benchmark scores to predict performance on factory images.

## Prompting tips that work

- Be specific: ask for exactly what you need ("Return JSON with keys `object`, `count`, `damaged`").
- Give **one example** (few-shot) if the model supports multiple images.
- Ask it to **point/box** the evidence for verification.
- Use **crops** from a detector to focus on small regions; send high resolution where details matter.
- Lower the **temperature** for extraction tasks.

:::interview Questions you may get
- "Describe the architecture of LLaVA." CLIP/SigLIP vision encoder → MLP projector → LLM; image tokens are prepended to the prompt; trained in two stages (connector alignment, then instruction tuning).
- "What does the connector do and what options exist?" Maps visual features into the LLM embedding space: linear/MLP, Q-Former/Perceiver (fixed queries), token merging, cross-attention.
- "Why is image resolution a problem for VLMs?" More patches mean more tokens, quadratic attention and context use; tiling and token merging trade accuracy for cost.
- "How do you reduce hallucination?" Better data (negatives, grounding), preference tuning, higher resolution, prompts asking for evidence, verification with a detector or a second pass.
- "How would you use a VLM in a robot cell?" For high-level checks and descriptions on keyframes, with a classical or fast detector/tracker in the real-time loop and validated, schema-constrained outputs.
:::

:::problem A customer wants a VLM to read serial-number labels (small text) on products moving on a conveyor at 20 items/second. Is a VLM suitable? What would you build? {level=medium tags="vlm,ocr,latency"}
Think about throughput, accuracy and cost.

:::solution Model answer
A general VLM on every frame is too slow and costly for 20 items/s, and small text is a known weakness. Build a pipeline: a fast detector (YOLO) finds and crops the label; a dedicated OCR model (PaddleOCR/TrOCR or a fine-tuned recogniser) reads it; validate with format rules and checksums. Use the VLM only as a fallback for low-confidence reads or for rare label formats, on a few frames per second asynchronously. Measure the character-level accuracy on real data and handle blur with a strobe/exposure setup and a trigger.
:::
:::

:::keypoints
- VLM = vision encoder (CLIP/SigLIP) + connector (MLP, Q-Former, merging) + LLM; image tokens are placed before the text prompt.
- Training: align the connector, then instruction-tune (LLM often with LoRA); high resolution costs many tokens.
- Strong at VQA, documents, grounding and reasoning; weak at counting, small text, spatial relations and real-time use.
- Evaluate on your own images; use VLMs for high-level, low-rate decisions and keep fast specialist models in the loop.
:::
