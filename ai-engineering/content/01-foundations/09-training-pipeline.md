A raw pretrained model is a brilliant autocomplete, not an assistant. Ask it "What is the capital of France?" and it may continue with three more quiz questions. Turning it into something helpful, honest and safe takes several more stages. Knowing the pipeline helps you understand **why models behave the way they do**, and where your own fine-tuning would fit.

:::flow The modern model pipeline
Data | collect, filter, deduplicate, mix
Pretraining | predict the next token on trillions of tokens
Mid-training | long context, code, maths, data annealing
Supervised fine-tuning (SFT) | learn the chat format and good answers
Preference tuning | RLHF / DPO / AI feedback
Reasoning RL | reward correct final answers
Evaluation + safety | benchmarks, red-teaming, release
:::

## Stage 1: data

The data stage is where most quality comes from.

- **Sources:** web crawls (Common Crawl and others), books, code (GitHub), scientific papers, Wikipedia, forums, licensed data, and increasingly **synthetic data** generated by other models.
- **Cleaning:** language identification, quality filtering (classifiers trained to recognise "textbook-like" text), **deduplication** (repeated text hurts), removing personal data and toxic content, decontamination (removing benchmark questions).
- **Mixing:** the proportion of code, maths, languages and domains is a major design choice. Small high-quality datasets like **Textbooks Are All You Need** ([paper](https://arxiv.org/abs/2306.11644)) showed that quality can substitute for quantity.

:::tip The AI engineer's takeaway
"Garbage in, garbage out" applies to your fine-tuning and RAG data too, only more so. A few thousand excellent, deduplicated examples usually beat a million noisy ones.
:::

## Stage 2: pretraining

:::def Pretraining
Training a randomly initialised network to predict the next token over trillions of tokens of text, by gradient descent on the cross-entropy loss. It costs most of the compute budget (millions of dollars or more for frontier models) and gives the model its knowledge and abilities.
:::

The compute of a training run is well approximated by:

:::formula Training compute
C \approx 6 \, N \, D \quad\text{(FLOPs)},\qquad N=\text{parameters},\; D=\text{training tokens}
:::

Roughly 2·N·D for the forward pass and 4·N·D for the backward pass.

### Scaling laws

Kaplan et al. ([paper](https://arxiv.org/abs/2001.08361)) found that test loss falls as a smooth **power law** in model size, data and compute. Hoffmann et al., the **Chinchilla** paper ([paper](https://arxiv.org/abs/2203.15556)), refined it: for a fixed compute budget, parameters and tokens should grow **together**, at roughly **20 tokens per parameter**.

```python run title="Compute-optimal sizing (Chinchilla rule of thumb)" level=intermediate
import math

def chinchilla(compute_flops, tokens_per_param=20):
    # C = 6*N*D and D = r*N  =>  N = sqrt(C / (6*r))
    n = math.sqrt(compute_flops / (6 * tokens_per_param))
    return n, tokens_per_param * n

for c in [1e21, 1e22, 1e23, 1e24, 1e25]:
    n, d = chinchilla(c)
    print(f"C={c:7.0e} FLOPs -> N≈{n / 1e9:8.1f} B params, D≈{d / 1e12:7.2f} T tokens")

# H100-class GPU at ~40% utilisation of ~1e15 FLOP/s peak (rough)
c = 1e24
gpu_flops = 4e14
gpu_days = c / gpu_flops / 86400
print(f"\n1e24 FLOPs ≈ {gpu_days:,.0f} GPU-days ≈ {gpu_days / 1000:,.1f} days on 1,000 GPUs")
```

### Why models are "overtrained" on purpose

Chinchilla minimises *training* cost. But a model is trained once and **served billions of times**, so inference cost matters more. Teams deliberately train smaller models on far more tokens (hundreds or thousands of tokens per parameter) so that the small model is as good as a larger compute-optimal one but cheaper to run. The Llama 3 report ([paper](https://arxiv.org/abs/2407.21783)) describes training 8B-70B models on ~15 trillion tokens, far beyond Chinchilla-optimal.

Use the simulator to see the trade-off:

```viz algo=scaling title="Compute budget → model size and tokens"
compute = 1e24
```

```python run title="Fit a power law to loss vs compute (numpy)" level=advanced
import numpy as np

# synthetic "losses" following L = a * C^(-b) + irreducible, with noise
rng = np.random.default_rng(0)
C = np.logspace(18, 24, 12)
true_a, true_b, floor = 8e2, 0.12, 1.7
loss = true_a * C ** (-true_b) + floor + rng.normal(scale=0.005, size=C.size)

# fit the reducible part on a log-log plot: log(L - floor) = log a - b log C
y = np.log(loss - floor); x = np.log(C)
slope, intercept = np.polyfit(x, y, 1)
print(f"fitted exponent b ≈ {-slope:.3f} (true {true_b})")

# extrapolate to a run 10x bigger than anything we have
C_big = C[-1] * 10
pred = np.exp(intercept) * C_big ** slope + floor
print(f"predicted loss at {C_big:.0e} FLOPs: {pred:.3f}")
```

This is why labs can predict how good a run will be before paying for it: they fit small runs and extrapolate.

## Stage 3: supervised fine-tuning (SFT)

:::def Supervised fine-tuning (SFT)
Continue training on a curated set of (prompt, ideal response) pairs, in the chat format. Same next-token loss, but computed only on the **response** tokens. It teaches the model to follow instructions, adopt a style and refuse appropriately. Papers such as FLAN ([paper](https://arxiv.org/abs/2109.01652)), InstructGPT ([paper](https://arxiv.org/abs/2203.02155)) and LIMA ([paper](https://arxiv.org/abs/2305.11206)) established that a relatively small set of high-quality demonstrations goes a long way.
:::

## Stage 4: preference tuning

SFT shows the model *good* answers. But "better" is easier to judge than to write. **Preference tuning** uses comparisons: for a prompt, humans (or other models) say which of two answers is better.

:::def RLHF (Reinforcement Learning from Human Feedback)
1. Collect comparisons of model outputs. 2. Train a **reward model** to predict which output people prefer. 3. Use reinforcement learning (PPO) to adjust the LLM to produce outputs with high reward, while staying close to the SFT model (a KL penalty) so it does not game the reward. Introduced for language by Ziegler et al. ([paper](https://arxiv.org/abs/1909.08593)) and scaled in InstructGPT.
:::

:::def DPO (Direct Preference Optimization)
A simpler method ([paper](https://arxiv.org/abs/2305.18290)) that skips the separate reward model and the RL loop: a single classification-style loss directly increases the likelihood of the preferred answer relative to the rejected one. Cheaper, more stable, and widely used in open recipes such as Tulu 3 ([paper](https://arxiv.org/abs/2411.15124)).
:::

:::def Constitutional AI / RLAIF
Instead of humans labelling every comparison, a model critiques and ranks outputs according to written principles (a "constitution") ([paper](https://arxiv.org/abs/2212.08073)). This scales feedback and makes the values explicit.
:::

```python run title="The DPO loss on one example" level=advanced
import numpy as np

def log_sigmoid(x): return -np.log1p(np.exp(-x))

def dpo_loss(logp_w, logp_l, ref_logp_w, ref_logp_l, beta=0.1):
    """logp_*: summed log-prob of the chosen (w) / rejected (l) answer under the policy / reference model."""
    margin = beta * ((logp_w - ref_logp_w) - (logp_l - ref_logp_l))
    return float(-log_sigmoid(margin)), float(margin)

# policy already slightly prefers the chosen answer relative to the reference model
print("loss, margin:", dpo_loss(-40.0, -55.0, -42.0, -50.0))
# policy prefers the REJECTED answer more than the reference does: loss is larger
print("loss, margin:", dpo_loss(-45.0, -48.0, -42.0, -50.0))
```

Minimising this pushes the policy to raise the chosen answer's probability and lower the rejected one's, relative to the reference model.

## Stage 5: reasoning with reinforcement learning

For problems with **checkable answers** (maths, code that passes tests, logic puzzles), you do not need human preference at all: reward the model when the final answer is verifiably correct. Letting the model generate long chains of thought and reinforcing the ones that end in correct answers makes reasoning behaviours emerge (checking its work, backtracking, trying alternatives). This is **RL with verifiable rewards (RLVR)**.

The open recipe is described in DeepSeek-R1 ([paper](https://arxiv.org/abs/2501.12948)), which uses **GRPO** introduced in DeepSeekMath ([paper](https://arxiv.org/abs/2402.03300)): sample a *group* of answers per prompt, score each, and push probability toward those scoring above the group average, with no learned value network.

```python run title="GRPO's core idea: advantages relative to the group" level=advanced
import numpy as np

# 6 sampled answers to the same maths question; reward 1 if the final answer is correct
rewards = np.array([1, 0, 0, 1, 0, 0], dtype=float)
adv = (rewards - rewards.mean()) / (rewards.std() + 1e-8)      # group-relative advantage
for i, (r, a) in enumerate(zip(rewards, adv)):
    print(f"sample {i}: reward={r:.0f} advantage={a:+.2f}  -> {'raise' if a > 0 else 'lower'} its probability")
```

A second way to buy accuracy is **test-time compute**: let the model think longer, sample many answers and vote, or search ([paper](https://arxiv.org/abs/2408.03314), [s1](https://arxiv.org/abs/2501.19393)). Reasoning models spend more tokens per answer to get better ones, so the "effort" or "thinking" setting in an API is a **cost-quality dial**.

## Stage 6: evaluation and safety

Before release, models are evaluated on benchmarks, red-teamed for misuse, and examined for biases and failure modes. Safety training (refusal behaviour, honesty) is mixed into SFT and preference tuning. Later lessons cover how *you* evaluate in your own context.

## What this means when you build

| Fact about training | Practical consequence |
|---|---|
| Pretraining ends at a **knowledge cutoff** | Models do not know recent events: use search or RAG |
| Models are trained to be **helpful and agreeable** | They can be sycophantic: ask for critique, include disconfirming checks |
| Post-training teaches **formats and refusals** | Behaviour shifts between model versions; pin versions and re-run evals |
| Reasoning RL rewards **final answers** | Great on verifiable tasks; weaker where "correct" is subjective |
| Larger, longer-trained models cost more per token | Route easy tasks to small models |

```quiz
? Roughly how many FLOPs does pretraining take for a model with N parameters on D tokens?
- N + D
+ 6 × N × D
- N × D²
> About 2ND for the forward pass and 4ND for the backward pass.

? Why do many labs train small models on far more tokens than Chinchilla recommends?
- Because tokens are free
+ The model is trained once but served many times, so a smaller model that matches a larger one saves inference cost
- Because small models cannot overfit
> Chinchilla optimises training cost; production cares about total cost including inference.

? What does DPO remove compared with classic RLHF?
+ The separate reward model and the reinforcement-learning loop
- The need for any preference data
- The base model
> DPO optimises a single loss on preference pairs directly.

? Why does reasoning RL work best on maths and code?
- Those tasks are short
+ Correctness can be checked automatically, giving a cheap, reliable reward
- Humans dislike them
> Verifiable rewards avoid reward-model errors.
```

:::problem Explain the difference between pretraining, SFT and RLHF to a product manager. {level=easy tags="training,alignment"}
Use one analogy and one sentence for each.

:::solution Model answer
Think of training a new employee. **Pretraining** is reading the entire library: broad knowledge but no job skills. **SFT** is shadowing a mentor and studying model answers: it learns the job's format and tone. **RLHF/preference tuning** is receiving feedback on which of two drafts the customer preferred: it refines judgement toward what people actually want. Reasoning RL is practising problems with an answer key.
:::
:::

:::keypoints
- Pipeline: data → pretraining (next token) → SFT → preference tuning (RLHF/DPO/AI feedback) → reasoning RL → evaluation and safety.
- Compute ≈ 6·N·D; Chinchilla says ~20 tokens per parameter for training-optimal, but production models are overtrained to make inference cheaper.
- SFT teaches format and behaviour; preference tuning teaches what people prefer; RLVR teaches reasoning by rewarding verifiably correct answers.
- Test-time compute (thinking longer, sampling more) is a second scaling axis you control through effort settings.
- Knowing the pipeline explains cutoffs, sycophancy and version-to-version drift.
:::
